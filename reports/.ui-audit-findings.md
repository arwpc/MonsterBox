### D9 — STT audio-event tags are matched as if spoken [Low-Medium] [CONFIRMED mechanism]
- Order history is polluted with entries like `"[outro jingle]" -> refused: no_verb`
  (4 of them between 8:37:46 and 8:37:58 PM during this audit).
- Cause: services/followOrders/orderMatcher.js:63 normalizeTranscript does
  `.replace(/[^\w\s']/g, ' ')` which strips the BRACKETS but keeps the words inside, so a
  Scribe non-speech tag becomes an ordinary phrase and is run through matching.
- Proven: `[glance left]` matches pose "Glance Left" at confidence 1, identically to the
  bare phrase `glance left`. `[  glance   left  ]` also matches.
- False-trigger risk TESTED AND NOT REPRODUCED: `[door closing]`, `[music]`,
  `[footsteps approaching]`, `[lights turning on]`, `[outro jingle]` ALL return no_verb,
  because findVerb needs exact base forms ("close", "turn on") and Scribe tags are
  gerund/noun phrases. So this is history pollution + wasted cycles + a latent vector,
  NOT a demonstrated false-trigger. Scored Low-Medium accordingly.
- Fix: drop transcripts matching /^\s*\[[^\]]*\]\s*$/ before matching/logging.

## PAGE: /scenes (Animation Studio)  (console: 0 errors, 0 warnings)

### D15 — Scene delete is IMPOSSIBLE: the confirm dialog's own backdrop swallows the click and cancels [HIGH] [CONFIRMED FUNCTIONAL BLOCKER]
- Repro: /scenes -> pick a scene -> trash icon -> confirm dialog appears -> click "Delete scene".
- What happens: the click lands on `div.mb-modal-backdrop`, which carries the attribute
  `data-studio-confirm-cancel`, so the dialog CANCELS. The scene is not deleted.
- Proof: dispatched a click at the exact centre of #studioConfirmOk. elementFromPoint at that
  point returned `mb-modal-backdrop` (hasCancelAttr=true); afterwards
  getComputedStyle(#studioConfirm).display === 'none' (dialog closed) and the scene
  "UI-AUDIT-scene-delete-me" (id 112) was STILL PRESENT on disk. 9 scenes before, 9 after.
- Root cause (stacking): `.mb-modal-backdrop` is a CHILD of `div#studioConfirm.mb-modal`
  (z-index 1050, position fixed — so the modal establishes a stacking context). Inside it:
      .mb-modal-backdrop  -> position: fixed,  z-index: 900   (full viewport 1430x900)
      .mb-modal-dialog    -> position: static, z-index: auto  (the actual content, y=343 h=214)
  A positioned, z-indexed child paints ABOVE a statically positioned sibling regardless of the
  static one coming later in the DOM. So the backdrop covers its own dialog's footer.
  Both #studioConfirmCancel and #studioConfirmOk measured reachable=false.
- Note the two buttons are NOT equally harmed: Cancel is also unclickable, but the backdrop
  performs a cancel anyway, so Cancel appears to work while Delete silently cannot.
- Fix: `.mb-modal-dialog { position: relative; z-index: 1001; }` (any value above the
  backdrop's 900), or render the backdrop as a preceding SIBLING of `.mb-modal` rather than
  a child.
- Affects the shared `mb-modal` component, so any other dialog built the same way is suspect.
  (#addStepModal / #newPoseModal / #storiesModal are Bootstrap `.modal fade` and use a
  different mechanism — they were display:none and not exercised here.)

### D28 *** CRITICAL — the servo daemon wedges and silently swallows EVERY servo command ***
[CRITICAL] [PROVEN, ROOT-CAUSED, AND FIXED DURING THE AUDIT]

WHAT HAPPENED
  Partway through the audit every servo stopped physically moving while every layer of the
  stack kept reporting success. Poses, scenes, the head sweep, jaw animation, Manual Controls
  and direct CLI calls all returned success; nothing moved.

PROOF CHAIN (each step independently verified)
  1. `POST /api/calibration/15/goto` -> 200 OK, UI showed "Position: 0.50".
     Direct I2C register read: UNCHANGED.
  2. `servo_cli.py move_to_pca 0 97 64` -> {"ok":true,"message":"PCA9685 ch0 set to 97.0 degrees"}.
     Register: UNCHANGED.
  3. `servo_cli.py move_to_pca 3 60 64` -> success. Register ch3: UNCHANGED at 932.6us.
  4. RAW smbus write to ch3 (bypassing the whole app): off 191 -> 239 IMMEDIATELY.
     So the I2C bus, the PCA9685 and the wiring were all healthy.
  5. Probed the daemon socket directly:
        {"cmd":"ping"}                                  -> {"status":"pong"}
        {"cmd":"set_angle","channel":3,"angle":75,...}  -> {"status":"ok","channel":3,"angle":75.0}
     Register after: UNCHANGED. The daemon ACKED and did not write.
  6. Daemon self-report:
        {"cmd":"stats"} -> {"commands":6167,"errors":0,"reinits":0,"uptime_s":7811}
        {"cmd":"state"} -> {"channels":{"64:0":296,"64:3":264}}
     Its own cache said ch0=296 / ch3=264 while the chip held 355 / 239.
     SIX THOUSAND commands, ZERO errors, and its state had diverged from the hardware.
  7. Killed the daemon (pid 1534, uptime 2h10m). Re-ran the IDENTICAL command that had just
     failed: `move_to_pca 0 97 64` -> register moved 355 -> 312. WRITES LANDED.
  8. App path re-verified after respawn: `POST /api/calibration/15/goto {"p":0.6}` ->
     {"success":true,"drivenAngle":108}; register 1635.7us = 107.6deg. Correct.
     Fresh daemon (pid 15443) works correctly.

ROOT CAUSE / MECHANISM
  `python_wrappers/pca9685_control.py:61` routes every servo write through the Unix socket
  `/tmp/monsterbox-servo.sock` when it exists, falling back to direct I2C only when the socket
  is missing or stale (:307-327). The long-lived daemon is therefore a single point of failure
  for ALL servo motion on the node. That instance degraded into a state where
  `servo_daemon._write()` -> `write_channel()` raised no OSError, cached the intended value in
  `_last_off`, and returned success — but the bytes never reached the chip. Because no
  exception was raised, `handle_command` returned {'status':'ok'} and every caller above it
  reported success. `errors: 0` across 6167 commands.
  Not the broken-channel guard: I verified `mb_safety.broken_channels('3')` correctly returns
  only {4:..., 5:...}; ch0 and ch3 were allowed.
  Not a duplicate daemon: single instance, sole holder of the socket and /dev/i2c-1 (lsof).
  Not the chip: MODE1=0x00 MODE2=0x04 PRESCALE=0x79 (~50.3Hz, correct) and raw writes worked.

WHY IT MATTERS MORE THAN ANY OTHER FINDING
  This is the exact failure the daemon's own docstring was written to prevent:
    "a caller that hears {'status':'ok'} for a pulse that never left the chip reports phantom
     motion all the way up to the operator — the bench saw 'Moved to 60 deg' while zero pulses
     went out (2026-08-22, the knight's magic box on a denied channel)."
  Their guard raises ChannelDenied for the DENIED-CHANNEL case only. There is no equivalent
  verification for the case where the write path itself stops working. On a live show night an
  operator would see a fully green UI and a motionless animatronic.

SUGGESTED FIXES
  * After each write, read the channel back and compare against `_last_off`; on mismatch,
    `_drop_bus()`, re-`_ensure()`, retry once, and raise if it still disagrees. The daemon
    already owns the bus so a read-back is cheap.
  * Add a watchdog: if a read-back mismatch occurs, log loudly and exit non-zero so Node's
    existing respawn (it already logs "Jaw daemon exited unexpectedly") recovers it.
  * Expose `{"cmd":"stats"}` errors/uptime on a health endpoint so a wedged daemon is visible.
  * Consider bounding daemon lifetime, since a fresh instance works and a 2-hour-old one did not.
