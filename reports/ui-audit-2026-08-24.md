# MonsterBox UI Audit — Orlok (192.168.8.120:3000), v10.5.0

**Audited:** 2026-08-23 20:17 → 2026-08-23 22:20 CDT (two passes)
**Method:** Interactive Playwright MCP against a live production node driving real hardware.
Round 1 was breadth (every page, console, settings round-trips, real hardware). Round 2 went
deeper on the layers round 1 missed: the **network layer**, **every tab**, **every dropdown
option swept end-to-end**, and **structural DOM bug classes** (duplicate ids, unnamed controls,
unlabeled fields, broken images, heading structure) — plus code-level root-causing.
**Pages covered:** 23. **Defects: 43. Verified passes: 113.**
**Nothing was committed.**

## 1. Summary verdict

**One critical defect, four high, and a long tail — against a genuinely well-built application.**

The headline is not a UI bug at all. **The servo daemon wedged mid-audit and silently swallowed
every servo command on the node while every layer reported success.** Poses, scenes, sweeps, jaw
animation, Manual Controls and direct CLI calls all returned `success: true`; nothing moved. I
root-caused it to the daemon acknowledging writes it never sent (6167 commands, `errors: 0`, its
own cache diverged from the chip), fixed it by restarting the daemon, and verified writes land
again end-to-end. **Had this happened on Halloween night the UI would have looked perfectly
healthy while Orlok stood still.** Full proof chain in D28.

The second headline: **I found a writer for your open `tts-config` clobber bug.** Opening
`/ai-settings/tts` and clicking Save — touching nothing — silently changed `stability` from 0.25
to 0.3, because the slider's `step="0.1"` cannot represent 0.25.

Against that, the codebase is in better shape than these findings suggest. Across 23 pages:
**zero console errors, zero console warnings, zero 4xx/5xx responses, zero duplicate element
ids, zero broken images**, and of ~1,500 buttons audited exactly one lacks an accessible name.
Every settings round-trip I ran persisted and restored correctly. And the two things you
specifically asked me to cross-check came back clean, including the important one: **the jaw
multi-config write hazard does not reproduce** — I made a non-first config active, changed it,
and the write landed on the active config with `configs[0]` untouched, then actually reached
playback and delayed the jaw by the configured amount.

You were right that round 1 under-tested. Round 2 found 17 more defects, including the critical
one, by looking at the network layer and sweeping dropdowns rather than just reading pages.

## 3. Defects

### CRITICAL

**D28 · the servo daemon wedges and silently swallows every servo command · FIXED DURING AUDIT**
Mid-audit all servo motion stopped while every layer reported success. Proof chain, each step
independently verified:
1. `POST /api/calibration/15/goto` → 200, UI showed "Position: 0.50". Register **unchanged**.
2. `servo_cli.py move_to_pca 0 97 64` → `{"ok":true,"message":"PCA9685 ch0 set to 97.0 degrees"}`. Register **unchanged**.
3. Raw `smbus` write to ch3 → register moved 191→239 **immediately**. So bus, chip and wiring were healthy.
4. Daemon socket probe: `{"cmd":"set_angle","channel":3,"angle":75}` → `{"status":"ok","channel":3,"angle":75.0}`. Register **unchanged**. The daemon acked and did not write.
5. Daemon self-report: `{"commands":6167,"errors":0,"reinits":0,"uptime_s":7811}`, and `state` → `{"64:0":296,"64:3":264}` while the chip held **355 / 239**. Six thousand commands, zero errors, cache diverged from hardware.
6. Killed pid 1534. Re-ran the identical failing command → register moved **355 → 312**. Writes landed.
7. App path re-verified: `goto {p:0.6}` → `drivenAngle:108`, register 1635.7µs = 107.6°. Fresh daemon (pid 15443) correct.

Mechanism: `pca9685_control.py:61` routes **every** servo write through
`/tmp/monsterbox-servo.sock` when it exists, so the long-lived daemon is a single point of
failure for all motion. That instance reached a state where `_write()` → `write_channel()` raised
no `OSError`, cached the intended value in `_last_off`, and returned success while the bytes never
reached the chip. Ruled out: the broken-channel guard (`mb_safety.broken_channels('3')` correctly
returns only `{4,5}`), duplicate daemons (single instance, sole holder of socket and
`/dev/i2c-1` per `lsof`), and the chip (`MODE1=0x00 MODE2=0x04 PRESCALE=0x79` ≈ 50.3Hz, raw
writes worked).

This is precisely what the daemon's own docstring exists to prevent: *"a caller that hears
`{'status':'ok'}` for a pulse that never left the chip reports phantom motion all the way up to
the operator."* Their guard raises `ChannelDenied` for the denied-channel case only; there is no
verification for the write path itself failing.

**Fix:** read the channel back after each write and compare against `_last_off`; on mismatch
`_drop_bus()`, re-`_ensure()`, retry once, then raise. Add a watchdog that exits non-zero on
mismatch so Node's existing respawn recovers it. Expose `stats` on a health endpoint. Consider
bounding daemon lifetime — a fresh instance works, a 2-hour-old one did not.

### HIGH

**D22 · `/ai-settings/tts` · Save silently rewrites his voice — a writer for the known clobber bug**
Clicking "Save Configuration" without touching any control changed `stability` **0.25 → 0.3**.
The slider is `step="0.1"`; 0.25 is not representable, so the page loads the real value
(`ai-settings-tts.js:72-74`) and the input immediately snaps it, then posts the snapped value.
`similarityBoost` and `style` are also `step="0.1"`. Your KNOWN-BUGS entry lists the writer as
unknown — this is one. It cannot explain a wrong `voice_id` or `model`, so others may remain.
**Fix:** `step="0.05"`, or post the fetched value unless the operator moved the control.

**D15 · scene delete is impossible — a modal's own backdrop swallows the click · 5 views**
Clicking "Delete scene" **cancels**. `elementFromPoint` at the button centre returns
`div.mb-modal-backdrop`, which carries `data-studio-confirm-cancel`; the dialog closed and scene
112 remained on disk (9 before, 9 after). Cause: the backdrop is authored as a **child** of
`.mb-modal` with `position:fixed; z-index:900` (components.css:670) while `.mb-modal-dialog`
(:686) sets no `position` and no `z-index`, so it stays static and loses the stacking contest.
Affected (backdrop as child): `scenes/studio.ejs:269` (proven), `setup/jaw-animation.ejs:268`
(**so jaw-config delete is also dead**), `scenes/scene-editor.ejs:118`, `scenes/scenes.ejs:101`,
`setup/unified-calibration.ejs:296`. Safe (backdrop as sibling): orchestration, schedule,
audio-library, goblin-management, video-library, and models/system/calibration which build it in
JS. Behaviour differs by page: studio's backdrop cancels, jaw's has no cancel handler so the
button is simply inert. **One-line fix:** `.mb-modal-dialog { position: relative; z-index: 1; }`

**D4 · head co-expression during speech is permanently dead**
Every utterance logs to `.err`: `[speech-expression] character 3 pan servo 15 has no configured
safe window — co-expression disabled` (`speechExpressionService.js:141`). But part 15 **has** real
calibration: `calibration_profiles.json` key `3:15` → `bounds {5,180}`, `autoGenerated: false`,
`lastCalibratedAt 2026-08-23T21:42:45Z` — calibrated the same day — with a `center` preset at 92°.
`/setup/head-animation` reads it correctly and renders "Head on a Swivel (5° – 180°)". The failing
service resolves only from `getPartSafety()` → `hardware-safety.json`, deliberately emptied
2026-08-20, so `lo`/`hi` are always null. No UI reports the feature is off or why.
**Fix:** resolve bounds the way head-animation does. Also stale: the note at `poses.json:89`
claiming part 15 has no real bounds predates the calibration.

**D18 · switching character silently re-points this node's physical channels**
Switching Orlok's node to Mina re-mapped the same PCA9685: `ch0 → part 10 "Servo Channel Laser"`
(physically Orlok's Head), **`ch4 → part 1 "Jaw"` (physically Orlok's dead Elbow on the fused
rail)**, ch3/ch5 unmapped. Restored on switching back. So a command for "Mina's jaw" energises
Orlok's broken elbow. Nothing moved only because every superpower was off.
**Fix:** warn (or refuse hardware commands) when the resolved character isn't this node's own.

**D8 · `/setup/follow-orders` · section header contradicts its own buttons**
The `h3` reads *"Try a phrase (dry run — matches against the SAVED config, never moves
hardware)"* and contains both "Match" (a true dry run) and **"Match + Execute"**. I clicked the
latter with "glance right" and it physically moved part 15 (`Pose "Glance Right" completed in
829ms`). The pose dropdown offers Arm Raise Full, Elbow Home, Right Arm Reach — all broken parts.

### MEDIUM

**D29 · servo pulse window disagrees between code and calibration.** `pca9685_control.py:57-58`
uses `SERVO_MIN_US=500` / `SERVO_MAX_US=**2400**`; `calibration_profiles.json` declares
`usMax=**2500**` for both servos. Every angle command falls short, scaling with angle: ~4.5° at
90°, ~9° at 180°. Measured: commanded 97° → 1523.4µs, which reads as 92.1° on the profile's
scale. So the jaw's calibrated 90° max physically reaches ~85.5°, and part 15's 180° reaches
~171°. Every calibrated window is silently under-travelled. Fix: read per-part `usMin`/`usMax`
from the profiles instead of hardcoding a global.
