# v11 Calibration UI Sweep — Usability / Consistency / Redundancy
Date: 2026-08-21 · Node: Orlok (dev seat) · Read-only audit; no hardware commanded, no files written outside /tmp.
Surfaces read: views/setup/calibration.ejs (all 6412 lines in sections), views/setup/unified-calibration.ejs,
routes/setup/calibration.js (all), server/calibration/router.js, server/calibration/store.js,
server/calibration/adapters/*, services/jawAnimationSuperPowerService.js, services/headAnimationSuperPowerService.js,
services/hardwareService/{index,servo,pca9685}.js, controllers/partsController.js.
Live GETs against http://localhost:3100 for real payloads (parts list, profiles, markers, effective).

The page's storage model is the root cause of most findings. FOUR stores hold "calibration" for the same part:
1. `data/calibration_profiles.json` (bounds/presets/capability — the live one, via /api/calibration)
2. `parts.json` `markers[]` per part (legacy, still the LIVE fallback for jaw/head guardrails)
3. `parts.json` `config.simpleCalibration` (legacy, read by NOTHING at runtime, banned by the repo's own lint rule)
4. `data/character-3/servo_calibrations.json` (read only by the GPIO-servo path in services/hardwareService/servo.js; no UI writes it)
The page hosts editors for #1 and #3, dead JS for #2, and nothing for #4.

## SHOW-STOPPER

### F1. Sweep Test drives an UNMEASURED servo full-span 0→180 ×3 at 100% speed, and the UI displays the placeholder span as if it were a measurement
- Files: views/setup/calibration.ejs:1178-1186 (bounds display reads `profile.bounds` raw), :1463-1501 (runSweepTest uses `currentCalProfile.bounds` + `speedPct:100`), server/calibration/router.js:117-123 (`getOrAutoCreateProfile` returns getRaw — placeholder bounds included), :568-597 (goto clamps with `calibratedBounds(profile)` which WITHHOLDS a placeholder span → no clamp at all).
- Live evidence: `GET /api/calibration/15/profile` → `{"bounds":{"minAngle":0,"maxAngle":180},"autoGenerated":true,"calibrated":false}`. Profiles 3:4 (Elbow) and 3:5 (Forearm) are the same placeholder shape. The panel renders "Min: 0° / Max: 180°" identically to a measured window; the `calibrated:false` field the GET returns is used NOWHERE in calibration.ejs (grep: no consumer).
- Failure scenario: operator selects "Forearm Rotation" (part 5 — travel never measured, shares the blown-fuse rail with part 4), sees "Min 0° Max 180°" and presses "Sweep Test" ("verify range of motion" per its tooltip). The page drives 0↔180 three times at 100% with hardware-safety.json empty and the calibrated-bounds clamp inactive (placeholder withheld). This is precisely the incident class the hardware skill documents.
- Fix (smallest): in `updateCalibrationUI`, when `profile.autoGenerated`/`calibrated:false`, render bounds as "0° (unmeasured)" with a warning badge, and make `runSweepTest` refuse (or confirm loudly) when the profile is a placeholder. Blast radius: calibration.ejs only (~20 lines).

### F2. The markers subsystem is invisible and uneditable on this page, yet it is the LIVE fallback for jaw/head guardrails — and Orlok's jaw markers hold known-bad values one "Clear" click away from being in effect
- Files: views/setup/calibration.ejs:3785-4010 — a complete marker editor (Set Min/Mid/Max from current position, Go buttons, add/delete, validation) wired to DOM ids `setMinBtn/minValue/customMarkers/newMarkerName/addMarkerBtn` that DO NOT EXIST anywhere in the markup (grep of all views: only unified-calibration.ejs has an unrelated `setMinBtn` that writes profile bounds). Every handler is `if (el)`-guarded, so the whole subsystem no-ops silently. `renderBottomRail` (:3775-3783) still paints decorative "name · Min/Mid/Max" chips for every part.
- Runtime consumers: services/jawAnimationSuperPowerService.js:461-494 — profile wins only when real; a placeholder OR missing profile falls back to `part.markers` Min/Max. services/headAnimationSuperPowerService.js:174-186 same pattern.
- Live evidence: jaw (part 10) profile bounds = 33-98 (measured, trusted); jaw markers = Min 63 / Max 131 — which the jaw service's own comment (:473) calls "past the mechanical stops".
- Failure scenario: operator presses the panel's "Clear" button on the jaw (calibration.ejs:1832-1860 → DELETE /api/calibration/10/profile) intending to re-calibrate. From that moment the jaw guardrails silently come from the invisible markers: 63/131, past the mechanical stops. Nothing on any page shows those numbers or lets him fix them. First jaw-synced audio of the show grinds the jaw into its stop.
- Fix: either restore the markers card markup (the JS is complete) or, better, delete the dead JS and migrate/retire markers explicitly; at minimum make "Clear" warn when markers exist ("guardrails will fall back to Min 63/Max 131"). Blast radius: calibration.ejs + a one-time data migration.

### F3. Invert is split-brain: the calibration panel's "Invert Servo Direction" writes `capability.invert` (calibration moves only), while the Edit tab writes `config.invertDirection` (runtime moves only) — two toggles for one physical fact, each honored by a different execution path
- Files: calibration.ejs:1418 (`/api/calibration/:id/set-invert`) → server/calibration/router.js:735, :816-822 (adapters honor `cap.invert`); calibration.ejs:5271-5279 (`getEditConfigValues` servo → `config.invertDirection`). Runtime readers of `invertDirection`: services/hardwareService/index.js:256-276 (actuator jog/extend/retract), :763-839 (continuous rotate); services/poses/poseEngine.js:204. The runtime absolute-servo path `servo.moveToAngle` (index.js:662) accepts NO invert at all; router.js:92-93 states "part.config.invert is undefined for every part".
- Failure scenario: operator flips the panel's Invert on a backwards-wired servo, jogs and calibrates until everything looks right, saves presets/poses. At show time the scene/pose path (controlPart → moveToAngle, no invert) drives the servo MIRRORED relative to everything he verified on the calibration page. 120° verified on this page becomes 60° in the show.
- Fix: one canonical invert key read by both paths (capability.invert is already persisted per character in the profile store — make hardwareService consult it, or have set-invert also write config.invertDirection), and remove one of the two toggles. Blast radius: hardwareService/index.js + calibration.ejs (~30 lines).

## MAJOR

### F4. The "Safety" tab is a dead control: "Current limit (A)" and "Timeout (ms)" inputs are never loaded, never saved, and read by nothing
- Files: calibration.ejs:564-565 (visible tab, tooltip "Set current limits and timeout thresholds for safe operation"), :726-737 (the two inputs). Grep of the entire repo: `safetyCurrent`/`safetyTimeout` appear ONLY at these two lines — no load, no save handler, no server key. And per the operator ruling, no current cap exists anywhere in software.
- Failure scenario: operator types "8" A on the coffin actuator, believing an over-current shutoff now protects the circuit that has blown fuses before. Nothing is stored; nothing enforces. He then runs parts 4+5 together trusting the limit.
- Fix: delete the tab (nothing to migrate). Blast radius: ~15 lines of calibration.ejs.

### F5. "Simple Calibration" card is a ghost duplicate editor sitting one tab away from the real one: writes a key nothing reads, captures the TEXTBOX value as "current position", and its delete button calls a route that does not exist
- Files: calibration.ejs:621-643 (card in the Edit tab: "Set Minimum / Set Maximum / Add Named Position", tooltips say "Capture the current position"), :4022-4100 (logic). Writes `config.simpleCalibration` via routes/setup/calibration.js:796-867. Consumers of `simpleCalibration`: ONLY that route file and eslint-rules/no-legacy-calibration.js:30, where the identifier is BANNED as legacy. `sc_currentValue` (:4025-4036) for a servo reads whatever number is in the `angNum` input (an angle 0-180) — not the hardware position — and its prompt fallback asks for "position (0.000-1.000)", a different unit. `sc_del` calls `DELETE /setup/calibration/api/simple/:id/points/:name`; the router defines only GET /api/simple/:id, POST set-safe, POST points (lines 770/796/833) — the DELETE 404s (HTML), `r.json()` throws, and the catch swallows it: the point simply never disappears, with no message.
- Failure scenario: operator spends a calibration session on "Set Minimum/Set Maximum" here (the buttons toast success), then finds scenes, poses, jaw, sweep — everything — ignoring his limits, because the real bounds live in calibration_profiles.json which this card never touches. The REAL Set Min/Set Max sit in the right-hand panel of the same screen.
- Fix: delete the card and the three /api/simple routes. Blast radius: ~120 lines across two files.

### F6. Edit-tab "Save Changes" silently ERASES config keys written by other tabs (motion/head-tracking tuning, model overrides) — and its own Advanced JSON textarea is display-only for most part types
- Files: calibration.ejs:5260-5340 (`getEditConfigValues` rebuilds `config` from scratch: servo keeps only 7 keys; webcam only devicePath/deviceId/width/height/fps; microphone only deviceId/sampleRate/gain), routes/setup/calibration.js:578-583 (PUT does a top-level spread — `updates.config` REPLACES config wholesale). The Advanced JSON textarea (editConfig) is populated for every type (:5346) but read back ONLY in the motor/linear_actuator (:5155-5176) and stepper (:5187-5200) branches, and even there only a whitelist of keys — for servos, webcams, mics, speakers, edits typed into "Advanced Configuration (JSON)" are silently discarded on Save.
- Failure scenario: operator tunes head tracking in the Advanced tab ("Tracking settings saved" — writes `config.motionTracking`/`config.headTracking`, calibration.ejs:2334-2356), later corrects the same webcam's fps in the Edit tab and hits Save Changes → the tracking tuning and pan-servo assignment are gone without a word. Same for any Model/Overrides value on a servo.
- Fix: make PUT merge `config` (or have savePartChanges start from `{...selected.config}` instead of `{}`), and either honor or remove the JSON textarea for non-motor types. Blast radius: one function in calibration.ejs or 3 lines in the route.

### F7. Microphone "Sensitivity" slider is a 100% no-op and "Gain" never persists: both persist via `GET /setup/calibration/api/parts/:id`, a route that does not exist
- Files: calibration.ejs:3211-3223 (sensitivity: GET part → merge → PUT; there is no live-apply call, persistence is its ONLY effect), :3233-3253 (gain: applies live via /setup/audio/api/set-input-gain, then persists via the same GET-then-PUT), :6321-6330 (same pattern in the STT test panel). The router defines GET /api/parts, /api/parts/:id/effective, /api/parts/:id/markers — no bare GET /api/parts/:id (grep of routes/setup/calibration.js:412/748/890; single mount at server.js:433). The 404 returns HTML, `r.json()` rejects, the trailing `.catch(function(){})` swallows it: no toast, no save.
- Failure scenario: operator sets mic sensitivity for the show — slider moves, nothing anywhere changes, no error. Sets input gain — it works until the next reboot, then reverts, which reads exactly like the "settings that mysteriously revert" class in memory (settings-persistence-class).
- Fix: add `router.get('/api/parts/:id', ...)` (10 lines, character-aware like its siblings) or PUT directly with the already-loaded `selected.config`. Blast radius: one route or ~6 lines of view JS.

### F8. Continuous-servo CW/CCW jog buttons silently stop working at the estimated-position rail while reporting success
- Files: calibration.ejs:2790-2800 (CW/CCW → POST /nudge `{delta:±0.1}`), server/calibration/router.js:408-418 (non-absolute nudge: `newP = clampP(currentP + delta, bounds)` — clamped to [0,1]), server/calibration/adapters/ContinuousServoAdapter.js:170-175 (`delta < 0.01 → return {success:true,'Already at target'}` — no hardware command).
- Failure scenario: calibrating a continuous servo (Sir Dragomir's neck is `servoType:"continuous"`), the operator presses CW five times from center — estimated position saturates at 1.0 — and every further CW press shows "cw complete" while the servo does not move. It looks exactly like a dead servo or a broken page; the physical part may be nowhere near its real end.
- Fix: when the clamp saturates, return/display "estimated position at end of range — use raw jog or reset position" instead of success. Blast radius: nudge handler or adapter (~10 lines).

### F9. Overrides cannot be removed: clearing a field skips it, "Revert to Model" is a server-side no-op, and the Effective panel is updated optimistically even when the save FAILED
- Files: calibration.ejs:2056-2063 (`collectOverrideFields` skips empty fields), :2168-2175 (Revert posts `overrides:{}`), routes/setup/calibration.js:666 (`config = { ...prev, ...overrides }` — a merge can never delete a key, so `{}` changes nothing), calibration.ejs:2124-2131 (comment: "Reflect overrides in Effective panel regardless of backend outcome to satisfy UX expectations" — the panel shows the merged values even on `success:false`).
- Failure scenario: operator set `channel: 5` override by mistake, blanks the field (or presses "Revert to Model"), sees the Effective panel update — but parts.json still carries channel 5 and the servo keeps driving the wrong PCA9685 channel. Displayed value is not the value in effect, on the exact key that has driven wrong-channel incidents before.
- Fix: overrides POST should replace (or accept null-to-delete); drop the optimistic Effective update. Blast radius: one route handler + ~10 view lines.

### F10. Servo "Min/Max/Neutral Pulse" and "Rotation Range" override fields are ghosts — the runtime drive path never reads them
- Files: calibration.ejs:1955-1959 (OVERRIDE_SCHEMAS.servo offers minPulse/maxPulse/neutralPulse/rotationRangeDeg), services/hardwareService/index.js:687-689 (PCA9685 standard path sends only channel+angle to the daemon / `servo_cli.py move_to_pca` — pulse mapping is hardcoded in the wrapper), services/hardwareService/pca9685.js `moveServoToAngle` accepts minPulse/maxPulse but no caller passes part.config values. The hardware skill documents the same fact for servo_models.json ("dead data").
- Failure scenario: a servo only reaches ~160° of travel; operator raises Max Pulse to 2500 in Model/Overrides, saves, sees it in "Effective (merged)" — physical travel is unchanged forever, and he burns rig time chasing it.
- Fix: remove the four fields from the schema (or plumb them through to the wrapper — bigger change, don't). Blast radius: 4 lines of calibration.ejs.

### F11. Two parallel calibration pages exist and the "Calibrated" trust stamp lives only on the hidden one
- Files: /setup/calibration (nav-linked, unified-navigation.ejs:68) vs /setup/calibration/unified (views/setup/unified-calibration.ejs — reachable only via legacy redirects routes/setup/calibration.js:1020,:1264). The stamp endpoint POST /api/calibration/:partId/calibrated (router.js:270-343) — the ONLY way to bless/retire a measured window, which controls whether `calibratedBounds()` releases bounds to every runtime consumer — is called solely from unified-calibration.ejs:547. The main page cannot stamp, and (F1) cannot even display, calibration trust.
- Failure scenario: operator measures real bounds on the main page, but the part was earlier un-stamped (autoGenerated re-set true via the stamp API or a placeholder recreate) — runtime withholds his window and he has no control on the page he actually uses to see or change that.
- Fix: surface `calibrated` + the stamp toggle on the main page; then retire the unified page or clearly mark it. Blast radius: calibration.ejs (~40 lines).

## MINOR

### F12. Hardware test buttons report "Done" unconditionally — success is never checked
- calibration.ejs:3015-3019 (motor Run), :3049-3062 (stepper), :3071-3078 (light), :3084-3091 (LED): `.then(function(){ st.textContent='Done' })` with no `.ok`/`success` check; fetch resolves on 500s, and hardwareService returns `success:true, simulated:true` on fallback anyway. A refused or simulated move reads "Done". Motor default duration is 15000 ms but "Done" appears when the request returns.
- Fix: check `data.success` (and surface `simulated:true`) like the servo branch does.

### F13. `lastCalibratedAt` means "last written", not "last calibrated"
- server/calibration/store.js:238 stamps it on EVERY upsert (preset add, channel reconcile, auto-create); router.js auto-create sets it on a never-touched part (live: part 15 shows a today timestamp with `calibrated:false`). routes/setup/calibration.js:109 reports it as calibration status. Misleading in any UI/report that trusts it.

### F14. `?characterId` on the page URL is accepted by the server and then ignored by the client
- routes/setup/calibration.js:387-397 resolves it and passes `currentCharacterId` to the render; calibration.ejs never references `currentCharacterId` (grep: zero uses) — all client flows use `window.__MB_CHAR_ID` = the layout's `selectedCharacter` (views/layouts/master.ejs:101, server.js:340). A deep link like /setup/calibration?characterId=2 silently shows and edits the SELECTED character. Today the page is internally consistent (everything lands on selectedCharacter), but the parameter is a lie. Related asymmetries kept honest only by that accident: GET markers resolves via `readConfig().selectedCharacter` (routes/setup/calibration.js:872-887) while POST/DELETE markers use `resolveCharacter(req)`; `/api/parts/:id/model` and `/overrides` use global `loadParts()`/`saveParts()` (controllers/partsController.js → `cfg.dataPath`) while every sibling route uses `loadCharacterParts(characterId)`; `/api/standard_servo/:id/move` calls `controlPart()` WITHOUT `{characterId}` (routes/setup/calibration.js:1288) against the CLAUDE.md rule. Any future re-enable of ?characterId turns all four into cross-character writes.
- Fix: either honor the param end-to-end or strip it; align the four odd routes with their siblings now.

### F15. Preset field-name drift across writers
- The panel's addPreset writes `{name, position, angle}` (calibration.ejs:1594-1600); the setup-route savePosition writes `{name, angle, p}` (routes/setup/calibration.js:171-190); the scene executor reads `angle`/`p` only (services/scenes/sceneExecutor.js:70,87,112 — never `position`). A preset captured on this page for an OPEN-LOOP part (only `position`, no `p`, no `angle`) resolves to `targetP = undefined` → NaN math in the executor's legacy path. gotoPreset's own fallback `{p: preset.position}` papers over it on-page, so the defect only appears at show time.
- Fix: write `p` (and keep `position` for backcompat) in addPreset.

### F16. Orphaned standard-servo pulse API fabricates presets
- POST /setup/calibration/api/standard_servo/:id/save-pulse (routes/setup/calibration.js:1297-1332) auto-creates presets min=0°/center=90°/max=180° as a side effect of saving a pulse — fabricated angles the executor will happily replay. No view calls it any more (grep across views/ and public/js: only the /move sibling at calibration.ejs:3856, itself part of the dead markers wiring, F2). Retire it with the markers cleanup.

### F17. Stale profile records for re-typed parts are never reconciled
- calibration_profiles.json holds `3:14` as an absolute-servo with measured bounds 2-180; part 14 is now a motion_sensor. Channel reconcile exists only for continuous servos (router.js:126-142). Harmless today, confusing in any profile listing, and a re-used part id inherits wrong-kind calibration.
